# Public-page maintenance

- Marketing copy is rendered through `t()` from `locales/en-US.json`. The homepage and About page also contain page-specific inline CSS and JSON-LD.
- `sitemap.xml` is manually maintained. Update only materially changed public pages; do not derive `lastmod` from deployment timestamps. Preserve canonical URLs and the sitemap reference in `robots.txt`.
- Subscription display amounts in `api/appConfig.php` are cents. Visible homepage prices are translated strings; verify that structured offers match both sources.
- Syntax checks: `php -l index.php`, `php -l about.php`. Existing responsive audit: `php tests/responsive-css-audit-test.php`.
- Local public-page verification: `node tests/public-seo-test.js` against the running MAMP site at `http://localhost/DentaTrak` (override with `BASE_URL`). Set `VERIFY_PUBLIC_URLS=1` to check live canonical sitemap URLs and the professional profile; set `SEO_SCREENSHOTS` to an existing directory to capture screenshots. No login or database writes are needed.
- New test scripts and screenshots are ignored by the existing repository rules unless explicitly allowlisted. The public SEO verifier is retained locally; do not assume it exists in a fresh checkout.

# PMS integration event worker

- Queued Open Dental webhook events (`integration_external_events` -> fetch -> normalize -> exact-once case import) are drained by `IntegrationEvents::processDue()`.
- **Production**: Cloud Scheduler job `dtk-prod-integration-event-worker` POSTs `https://dtk-app-prod-1029275239454.us-east1.run.app/api/integration-event-worker.php` every minute with the `X-Queue-Worker-Token` header (Secret Manager `dtk-prod-queue-worker-token`, same mechanism as `notification-queue-worker.php`). Provisioning is idempotent via `scripts/provision-integration-worker.sh`, invoked at the end of `cloudbuild.yaml`. Overlapping invocations are safe (atomic claims).
- **Local development**: `php api/integrations/process-events.php [--limit=25] [--watch[=seconds]]` (CLI), or POST the endpoint with the dev `QUEUE_WORKER_TOKEN` header. Windows Task Scheduler alternative: run `php.exe C:\MAMP\htdocs\DentaTrak\api\integrations\process-events.php` every minute.
- Events are claimed atomically (conditional UPDATE with `claimed_at`), transient failures (network/timeout/5xx/429/eConnector offline) retry with bounded linear backoff (max 10 attempts, cap 300s, honors Retry-After), permanent failures park as `failed`, and stale `processing` rows are reclaimed 10 minutes after their last claim.

# DS Core scan retrieval (Primescan)

- `api/integrations/dscore/DsCoreScanSync.php` polls `GET /v1beta/digitalImpressions` for every active `ds_core` connection inside the per-minute `integration-event-worker.php` pass, gated on both `DS_CORE_CONNECT` and `SCANNER_INBOX`. `DsCoreScanConnector` (vendor `primescan`) normalizes impressions; `DsCoreClient` wraps the read-only business calls in `withAutoRefresh`.
- Polling cursor lives in `integration_connections.config_json.scan_poll` (no migration). Windows overlap (`DS_CORE_SCAN_OVERLAP_SEC`, default 300); per-page progress commits so interrupts resume via `page_token`. Env knobs: `DS_CORE_SCAN_INTERVAL_SEC` (300), `DS_CORE_SCAN_LOOKBACK_SEC` (86400), `DS_CORE_SCAN_MAX_PAGES` (10), `DS_CORE_SCAN_MAX_SCANS` (500). Cross-instance overlap prevented by `GET_LOCK('dscore_scan_sync_{id}', 0)`.
- Auth/business host separation: token endpoints on `DsCoreConfig::apiBaseUrl()` (global `api.dscore.com`), business APIs on `businessBaseUrl()` (regional, `api.r2.dscore.com` sandbox; override `DS_CORE_BUSINESS_BASE_URL`). Content downloads always send `fileType=STL`, verify `md5Checksum` from `.../content/{X-Content-Id}/checksum`, and handle plain-STL vs zip packaging (packaging is pending sandbox verification).
- **Practice allowlist (rollout gate)**: `DS_CORE_ALLOWED_PRACTICES` (comma-separated ids, env-only) is checked server-side on connection initiation (`beginAttempt`), callback completion (`handleCallback`), token refresh sweeps, scan polling, and every download via the connector's client resolution. UNSET/EMPTY permits NO practice; no role, plan, or admin override can widen it. `DS_CORE_CONNECT` alone can never reach a real practice.
- **Scope/limitation**: this is new-scan import with LIMITED revision detection - the signature covers models/estimated sizes/supported file types only, so changed content with identical metadata and file size is undetectable. The API exposes no updateTime/etag; do not describe this as complete revision synchronization.
- **Future sandbox test setup (same production host)**: the registered callback `https://dentatrak.com/api/dscore-callback.php` is immutable, so the first sandbox test runs on the live host with: `DS_CORE_ENVIRONMENT=sandbox`, sandbox Client ID/Secret from Secret Manager, `DS_CORE_CONNECT=true`, `SCANNER_INBOX=true`, and `DS_CORE_ALLOWED_PRACTICES=<internal test practice ids only>` - never a customer practice. The initiating session must belong to a test-practice admin; connection storage lands in that practice's `integration_connections` row. Customer practices remain unreachable because the empty/default allowlist denies them and admin overrides cannot widen it.
- Mocked regression: `php tests/dscore-scan-connector-test.php` (requires local dev DB on 3308, self-cleaning fixtures, no live calls).

# Medit Link scan retrieval (staging)

- `api/integrations/medit/MeditScanSync.php` polls `GET /v1/cases/search` (dateCreated window, ms epoch, page/size pagination) for every active `medit` connection inside the per-minute `integration-event-worker.php` pass, gated on both `MEDIT_CONNECT` and `SCANNER_INBOX`. `MeditScanConnector` (vendor `medit`) normalizes cases; `MeditClient` wraps read-only calls in `withAutoRefresh` and carries `x-meditlink-client-id` + `x-meditlink-group-uuid` headers. A per-case `GET /v1/cases/{uuid}` supplies `files[]` (the search row has none).
- Polling cursor lives in `integration_connections.config_json.scan_poll` (no migration needed for the cursor; `migrations/2026_10_30_medit_oauth.php` creates `medit_oauth_attempts` + `medit_webhook_events` and must run before enabling). Env knobs: `MEDIT_SCAN_INTERVAL_SEC` (300), `MEDIT_SCAN_OVERLAP_SEC` (300), `MEDIT_SCAN_LOOKBACK_SEC` (86400), `MEDIT_SCAN_MAX_PAGES` (10), `MEDIT_SCAN_MAX_SCANS` (500), `MEDIT_WEBHOOK_BATCH` (25). Cross-instance overlap prevented by `GET_LOCK('medit_scan_sync_{id}', 0)`.
- Auth/resource host separation per the OpenAPI guide: `/oauth/*` on `stage-openapi-auth.meditlink.com`, `/v1/*` on `stage-openapi-resources.meditlink.com` (`MEDIT_ENVIRONMENT=stage|production`; production hosts follow the same naming and are env-overridable pending vendor confirmation). Token exchange + refresh use `Authorization: Basic base64(client_id:client_secret)`; refresh passes `grant_type`/`refresh_token` as query params (documented). No PKCE (not in the guide). NO documented revocation endpoint - disconnect wipes local credentials inside the refresh lock and honestly reports `remote_revoked=false`.
- Group binding: `/v1/me` is called at connect time; `group.uuid` persists in `config_json.group_uuid` and is required for every resource call. Webhook tenant resolution matches deliveries to that bound uuid + active environment + allowlist.
- **Practice allowlist (rollout gate)**: `MEDIT_ALLOWED_PRACTICES` (comma-separated ids or `*`, env-only) is enforced on initiation, callback completion, token refresh, polling, webhook processing, and downloads. UNSET/EMPTY permits NO practice; `MEDIT_CONNECT` alone can never reach a real practice.
- Downloads: `GET /v1/files/{uuid}?type=stl` returns a presigned S3 url + `items[]` (entry name/size/base64-MD5). The presigned URL is fetched with NO auth headers and only over https on `*.amazonaws.com`/`*.meditlink.com` hosts. Packaging is 7z - extracted via `p7zip` (Dockerfile `p7zip-full`) with path/symlink/entry-count/expanded-size limits and per-entry MD5 verification; hosts without p7zip store the archive opaquely (documented degradation).
- **Webhook**: `api/medit-webhook.php` verifies `HMAC-SHA256(rawBody, MEDIT_WEBHOOK_SIGN_SECRET)` (fail closed when unset), dedups via `medit_webhook_events.dedup_key`, and records work durably - the worker's drain re-fetches each `case_uuid` directly (updates to older cases creation-polling can't see). The guide does NOT document the delivery signature header name: `MEDIT_WEBHOOK_SIGNATURE_HEADER` defaults to `x-meditlink-signature` and is overridable pending vendor confirmation.
- **Scope/limitation**: cases/search filters on dateCreated only - updates to older cases arrive via webhooks, not polling. File revision detection uses uuid+size+dateUpdated signatures; same-metadata/same-size re-scans are undetectable (documented gap).
- Mocked regression: `php tests/medit-integration-test.php` (requires local dev DB on 3308, self-cleaning fixtures, no live calls).

# Organization access scope (Scale foundation)

- There is no `organizations` table: the organization is the subscription owner's account. Every practice with `practice_users.is_owner = 1` for the same user shares that user's single `subscriptions` row (`api/subscription-owner.php`). There is no organization-administrator role; `practice_users.role='admin'` is practice-scoped only and `users.role='admin'` is platform-level.
- `api/organization-access.php` is the single resolver for "which practices may this user access in the current organization": `getAuthorizedOrganizationPractices($pdo, $userId, $anchorPracticeId)` (org owner gets all active org practices, everyone else only their explicit memberships), `userCanAccessOrganizationPractice()` for validating client-supplied practice IDs, and `buildAuthorizedPracticeScopeSql()` for scoping future cross-practice queries (empty scope renders `1 = 0`; no "all practices" bypass).
- `hasScaleAccess($pdo, $practiceId, $userEmail)` in `api/subscription-access.php` is the shared Scale entitlement gate for the consolidated view/Insights; it reuses trial/grace/bypass behavior via `hasPlanTierAccess()`.
- `PLAN_INCLUDED_PRACTICES` / `getIncludedPracticeCount()` in `api/plan-entitlements.php` hold the "Scale includes 5 practices" count; never hardcode it.
- Platform administrators (internal DentaTrak staff) are the `SUPER_USERS` email list in `api/appConfig.php` checked via `isSuperUser()` in `api/dev-tools-access.php`. `hasPlanTierAccess()`, `hasIntegrationAccess()`, `evaluatePracticeCreationEntitlement()`, and `api/billing.php` metering all treat super users as unrestricted; membership/permission checks are unaffected, so admins still only see authorized practices and cases.
- Administrative plan overrides live in `api/plan-overrides.php` (`admin_plan_overrides` keyed by subscription owner). An override changes the effective plan for entitlement only - never `subscriptions`, Stripe, or invoices - and applies to every practice the owner owns. Set/clear via Practice Administration (`admin-practices.php`) → Subscription tab → "Change Effective Plan" (`api/admin-practices.php?action=set_plan_override`, CSRF + super-user + audit-logged). Gates read `effective_plan` (or `getEffectivePlanForOwner()`), never `subscription_plan` directly, so purchased and effective plans stay distinct.
- Verification: `php tests/organization-access-test.php` and `php tests/plan-override-test.php` (local dev DB on 3308, self-cleaning fixtures).
- The consolidated "All practices" case view is a session-only scope (`$_SESSION['org_case_view']`) enabled via `api/set-case-view-scope.php` (Scale entitlement + >= 2 authorized practices required; `$_SESSION['current_practice_id']` stays the real anchor practice and switching practices clears the flag). `api/list-org-cases.php` serves the scoped list; every case-scoped endpoint resolves the case's actual practice via `resolveCaseScopePracticeId()` before `requireCaseAccess` - never trust a client-supplied practice ID. UI lives in `js/org-case-view.js` + `css/org-case-view.css`; `window.__orgCaseViewActive` guards single-practice behaviors (patient-search, view toggles). Verification: `php tests/org-case-view-test.php`.
- Organization Insights: `api/get-org-insights.php` serves aggregate metrics for the org scope (same entitlement/access resolution as the case view; practices where the user lacks `can_view_analytics` are excluded and disclosed). `api/org-insights-metrics.php` holds the pure metric math (workload "as of now", history by creation/completion date, on-time with due-edit guard, lab turnaround via the lab-performance service, monthly trend; all dates in ORG_INSIGHTS_TZ = America/New_York). UI in `js/org-insights.js` + `css/org-insights.css`; drill-down links only current-state metrics into the consolidated list via `window.orgCaseViewDrillDown`. Verification: `php tests/org-insights-test.php`.

# Commit-message attribution hook

- `.githooks/commit-msg` strips AI coding-tool attribution lines/trailers (`Generated with/by Devin`, `Generated with Windsurf`, `Co-Authored-By:` entries naming Devin, Windsurf, Codeium, Cascade, Cursor, Claude, Copilot, ChatGPT, OpenAI, Gemini, or other AI coding agents). Human `Co-Authored-By` trailers and normal message content are preserved.
- Git hooks are not shared automatically. Activate once per clone:
  `git config core.hooksPath .githooks`
- The hook is a POSIX shell script (works in Git Bash on Windows, macOS, Linux). Do not add attribution lines to commit messages manually; the hook will remove them.
